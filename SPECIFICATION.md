# DSH for VS Code — спецификация проекта

**Статус:** идея / pre-alpha
**Кодовое имя расширения:** `dsh-vscode`
**Идентификатор:** `victorkozachek.dsh-vscode`

---

## 1. Проблема и идея

DeepSeek Harness (DSH) — это агентный харнесс с сессиями, скилами, правилами (`AGENTS.md`), инструментами правки файлов, sandbox-политиками и оркестрацией субагентов. Сегодня он живёт в терминале и в Web GUI, то есть **вне редактора**: разработчик переключается между IDE и окном агента, а агент не знает, какой проект открыт, какие файлы в фокусе и что происходит в диагностике.

Идея: перенести полный функционал харнеса внутрь VS Code — самой популярной IDE — так, чтобы **воркспейс определялся автоматически по открытой папке**. При открытии папки расширение распознаёт проект, поднимает его контексты, скилы и правила и продолжает сессию с того места, где она остановилась. При переключении на другую папку — переключается и контекст агента.

Ключевой инвариант: **один VS Code — много проектов, у каждого свой изолированный контекст, и переключение между ними не требует перезапуска IDE или ручной перенастройки.**

---

## 2. Цели и не-цели

### Цели

1. Полноценный агентский опыт внутри VS Code: чат, вызовы инструментов, правки файлов, approval-диалоги, терминал — без переключения в браузер.
2. Автоматическое определение воркспейса по открытой папке (включая multi-root и remote-сценарии).
3. Восстановление контекста проекта: сессии, история, скилы, правила, память, настройки — при открытии папки и при возврате к ней.
4. Единая панель: сессии, задачи (kanban), инспектор контекста, настройки.
5. Сохранить совместимость с существующей экосистемой DSH: те же скилы, `AGENTS.md`, формат сессий, kanban-протокол, субагенты.

### Не-цели (в MVP)

- Переписывание агентного движка внутри расширения — расширение **управляет** DSH, а не заменяет его.
- Собственный inference-стек, прокси моделей, биллинг.
- Замена терминала и системы контроля версий.
- Мобильные клиенты и браузерное расширение.
- Публикация в Marketplace на этапе MVP (сначала VSIX из репозитория).

## 3. Пользовательские сценарии

### 3.1. Первый запуск в проекте

1. Пользователь открывает папку `~/projects/api-service`.
2. Расширение активируется, определяет корень воркспейса (realpath), ищет `.dsh/workspace.json` и `AGENTS.md`.
3. Если папка видится впервые — создаётся запись в локальном реестре воркспейсов и пустая сессия.
4. Если папка уже известна — восстанавливается последняя сессия, контекст, скилы и правила.
5. Status bar показывает: `DSH · api-service · workspace-write · idle`.

### 3.2. Смена папки (главный сценарий)

1. Пользователь делает `File → Open Folder…` → `~/projects/web-app`.
2. Расширение получает `onDidChangeWorkspaceFolders`, ставит старую сессию на паузу, но **не убивает процесс сразу** (grace period, по умолчанию 10 минут), чтобы быстрое переключение туда-обратно было мгновенным.
3. Загружается контекст нового проекта: манифест, правила, скилы, индекс файлов.
4. Панель DSH обновляется: заголовок, список сессий, активная задача, модель.
5. Чат продолжает работать в контексте нового воркспейса — никаких «забытых» файлов из прошлого проекта.

### 3.3. Multi-root workspace

Открыт `.code-workspace` с несколькими папками. Правило MVP: **первая папка — primary workspace**, остальные подключаются как дополнительные корни с объединёнными правилами (приоритет — у primary, конфликты показываются в инспекторе контекста). В v0.2 — явный выбор primary через панель.

### 3.4. Remote / WSL / SSH / Codespaces

Расширение исполняется на remote extension host. `dsh`-бинарь должен быть доступен на удалённой машине; расширение проверяет наличие и версию и, если бинаря нет, показывает инструкцию вместо падения. Пути и реестр воркспейсов — локальные для remote-хоста.

### 3.5. Возврат к проекту спустя дни

История сессий, изменённые файлы, открытые задачи и память проекта сохраняются в реестре и в `.dsh/` проекта. Возврат — как продолжение разговора, а не с чистого листа.

## 4. Модель воркспейса

### 4.1. Идентичность воркспейса

Воркспейс = корневая папка проекта. Идентификатор вычисляется как хеш от:

- канонического абсолютного пути (`fs.realpath`, без учёта регистра на macOS/Windows);
- remote-хоста (для SSH/WSL/Codespaces);
- `git remote origin` (если есть) — чтобы один и тот же проект, склонированный в разные места, не считался разными воркспейсами;
- имени папки — только как подсказка для UI, не как часть ключа.

Ключ: `<sha256[:16]>` → запись в реестре.

### 4.2. Реестр воркспейсов

Локальный файл `~/.dsh/workspaces/<id>.json` (путь настраивается) хранит:

```jsonc
{
  "id": "a1b2c3d4e5f60718",
  "path": "/Users/victor/projects/api-service",
  "remote": null,
  "gitRemote": "github.com/acme/api-service",
  "name": "api-service",
  "lastOpenedAt": "2026-11-09T15:40:00Z",
  "lastSessionId": "sess_01J...",
  "defaultModel": "deepseek-chat",
  "sandboxMode": "workspace-write",
  "approvalPolicy": "ask",
  "contextSnapshot": {
    "hash": "sha256:...",
    "skills": ["kanban", "office"],
    "rules": ["AGENTS.md", "docs/architecture.md"],
    "files": 1287
  }
}
```

Секреты в реестр не пишутся никогда.

### 4.3. Манифест проекта `.dsh/workspace.json` (опционально)

Проект может уточнить поведение:

```jsonc
{
  "name": "api-service",
  "defaultModel": "deepseek-chat",
  "sandboxMode": "workspace-write",
  "approvalPolicy": "ask",
  "skills": [".dsh/skills"],
  "rules": ["AGENTS.md", "docs/CONVENTIONS.md"],
  "context": { "ignore": ["dist/**", "*.lock"], "maxBytes": 262144 },
  "kanban": { "enabled": true }
}
```

Приоритет настроек: **workspace settings VS Code → `.dsh/workspace.json` → глобальные настройки расширения → значения по умолчанию**.

### 4.4. Жизненный цикл

```
не открыт → resolving → loading-context → ready → paused (другая папка) → teardown
```

- `resolving` — определение корня, чтение манифеста.
- `loading-context` — правила, скилы, индекс файлов; прогресс в status bar.
- `ready` — можно общаться и запускать инструменты.
- `paused` — процесс жив, но без активных ходов; освобождает лимиты.
- `teardown` — по таймауту или вручную; сессия сохраняется на диск.

## 5. Архитектура расширения

### 5.1. Компоненты

| Компонент | Ответственность |
|---|---|
| `WorkspaceResolver` | определение корня, remote, git remote, идентификатора; multi-root |
| `WorkspaceRegistry` | реестр воркспейсов, миграции, GC старых записей |
| `ContextLoader` | сборка контекст-пака: правила, скилы, память, индекс файлов, игноры |
| `DshBridge` | жизненный цикл процессов `dsh`, JSON-RPC-транспорт, мультиплексирование сессий |
| `SessionManager` | создание/возобновление/пауза сессий, история, восстановление после рестарта IDE |
| `TaskBoardProvider` | tree view задач kanban, синхронизация с `.kanban/tasks/*.md` |
| `ChatView` | WebView: лента сообщений, tool-call-блоки, инлайн-diff, approvals |
| `DiffService` | предпросмотр и применение правок, откат, конфликт-резолюция |
| `TerminalBridge` | запуск команд агента в интегрированном терминале, захват вывода |
| `StatusBar` | активный воркспейс, режим sandbox, состояние агента |
| `DiagnosticsBridge` | передача ошибок/предупреждений из VS Code агенту как контекст |

### 5.2. Транспорт к DSH

MVP: **stdlib JSON-RPC 2.0 поверх stdio**, процесс на воркспейс:

```
dsh serve --protocol=jsonrpc --cwd <workspace> --sandbox <mode>
```

- один процесс на воркспейс, N сессий внутри;
- запросы: `session.create`, `session.resume`, `session.list`, `turn.start`, `turn.cancel`, `tools.invoke`, `approval.resolve`, `context.reload`, `workspace.ping`;
- события: `token`, `tool.call`, `tool.result`, `approval.request`, `turn.done`, `error`, `status`;
- перезапуск процесса — с экспоненциальным backoff, состояние сессии восстанавливается из диска.

Альтернативы (исследовать в M1): переиспользование Web-сервера DSH по localhost HTTP+WS; нативный `dsh` CLI в режиме `--json`.

### 5.3. Точки интеграции с VS Code

- `vscode.workspace.onDidChangeWorkspaceFolders` — смена воркспейса.
- `vscode.window.registerWebviewViewProvider` — панель чата в боковой панели.
- `vscode.commands.registerCommand` — команды агента.
- `vscode.workspace.applyEdit` / `WorkspaceEdit` — правки с undo-стеком редактора.
- `vscode.languages.getDiagnostics` — контекст ошибок.
- `vscode.window.createTerminal` + shell integration — команды.
- `vscode.window.tabGroups` — открытые файлы и активный редактор как контекст.
- `vscode.env.clipboard`, `vscode.env.selection` — выделение как контекст.

## 6. Дизайн панели

### 6.1. Activity bar

Иконка DSH открывает контейнер с тремя view:

1. **Sessions** — список сессий воркспейса, группировка по дате, статус (active/paused), бейдж незавершённых задач.
2. **Tasks** — kanban-доска задач (todo / in-progress / in-review / testing / ready / merged), синхронизация с файлами.
3. **Context** — инспектор: какие правила и скилы загружены, размер контекста, что проигнорировано, кнопка «Перезагрузить контекст».

### 6.2. Основная панель (WebView в редакторе или боковая)

- Шапка: имя воркспейса, модель, режим sandbox, кнопка «Стоп».
- Лента: сообщения пользователя/агента, свёрнутые tool-call-блоки с диффом и статусом.
- Инлайн-approvals: «Разрешить», «Разрешить для этой сессии», «Отклонить», «Показать diff».
- Composer: многострочный ввод, вложения файлов и выделения, `@`-упоминания файлов и символов, история промптов.
- Статусная строка панели: токены, стоимость, длительность хода.

### 6.3. Дизайн-принципы

- Никаких модальных окон для рутинных действий — approvals инлайн.
- Всё, что меняет файлы, показывается диффом до применения.
- Панель не «прыгает»: фиксированная шапка, скролл только в ленте.
- Тёмная и светлая темы через `--vscode-*` переменные.
- Доступность: полная навигация с клавиатуры, ARIA, фокус-ловушки в диалогах.

## 7. Контексты, скилы и правила

### 7.1. Что поднимается при открытии папки

1. `AGENTS.md` (корень и вложенные каталоги) — правила проекта.
2. `.dsh/workspace.json` — настройки и переопределения.
3. Скилы: `~/.dsh/skills/*`, `.dsh/skills/*`, скилы плагинов.
4. Память проекта (если включена): история решений, договорённости.
5. Индекс файлов: дерево, размеры, языки; уважает `.gitignore` и собственные игноры.
6. Диагностика и открытые файлы — как «живой» слой контекста (опционально).
7. Kanban-задачи проекта — если включены.

### 7.2. Кэширование и инвалидация

- Контекст-пак кэшируется по хешу входов (mtime + размер файлов правил и скилов).
- Инвалидация: изменение `AGENTS.md`/манифеста/скилов, `git checkout`, явная команда «Reload Context».
- Изменения подхватываются watcher'ом с debounce 500 мс.

### 7.3. Приоритеты при конфликтах

Правило проекта > правило пользователя > встроенное. Конфликты не «затираются» молча — инспектор контекста показывает, что победило и почему.

---

## 8. Безопасность и approvals

- Sandbox-режимы DSH (`read-only` / `workspace-write` / `danger-full-access`) маппятся на настройки расширения; смена режима — явное действие пользователя.
- Approval-политика (`ask` / `auto` / `never`) — для каждого типа инструмента отдельно.
- Запись файлов вне воркспейса и сетевые вызовы — всегда требуют подтверждения, независимо от политики.
- Секреты: токены и ключи не попадают в контекст-пак (фильтр по именам и по `.gitignore`-паттернам), не логируются.
- Аудит: журнал approval-решений в `.dsh/audit.log` (опционально, с ротацией).

## 11. Этапы

### M0 — каркас (1–2 недели)

- Extension scaffold, активация, `WorkspaceResolver`, реестр, status bar.
- Панель-заглушка, команда «New Session».
- `DshBridge` со stdio JSON-RPC и одним тестовым методом.

### M1 — рабочий агент (3–4 недели)

- Чат с потоковыми ответами, tool-call-блоки, approvals.
- `ContextLoader`: `AGENTS.md`, скилы, индекс файлов, кэш и инвалидация.
- Правки файлов через `WorkspaceEdit` с диффом и откатом.
- Восстановление сессии после рестарта IDE.

### M2 — воркспейс-переключение (2–3 недели)

- Полный цикл смены папки: pause → load → resume, grace period, GC процессов.
- Multi-root, remote/WSL/SSH, обработка отсутствующего бинаря.
- Инспектор контекста и настройки.

### M3 — экосистема (2–3 недели)

- Kanban-панель, субагенты и их визуализация, терминал-мост, диагностика.
- VSIX-сборка, CI, документация, первые внешние тесты.

## 12. Критерии приёмки MVP

1. Открытие папки поднимает воркспейс без ручных действий; в status bar — корректное имя.
2. Смена папки переключает контекст: агент не видит файлы предыдущего проекта.
3. Возврат к папке восстанавливает последнюю сессию и историю.
4. Правка файла агентом показывается диффом и откатывается через undo.
5. Approval-запросы работают инлайн; «отклонить» останавливает инструмент.
6. Рестарт IDE не теряет сессию.
7. Multi-root не ломает определение primary-воркспейса.
8. Нет секретов в реестре, логах и контекст-паке.

## 13. Риски и открытые вопросы

| Риск | Митигация |
|---|---|
| Нестабильный lifecycle процессов DSH | supervisor с backoff, healthcheck, graceful shutdown |
| Дорогой контекст на больших репозиториях | индекс и ленивая загрузка, лимиты, инспектор |
| Расхождение версий расширения и `dsh` | проверка версии при старте, явное сообщение |
| Multi-root семантика неочевидна | primary-воркспейс + инспектор конфликтов |
| Windows-пути и WSL | тесты на трёх платформах в CI |
| Публикация в Marketplace и лицензия | решить до M3 |
| Безопасность автономных правок | дифф-предпросмотр, approvals, sandbox |

Открытые вопросы:

- Переиспользовать ли Web-сервер DSH вместо отдельного RPC-протокола?
- Где хранить память проекта — в `.dsh/` (в git) или в реестре (локально)?
- Нужен ли режим «несколько агентов в одном воркспейсе одновременно»?
- Как показывать субагентов: вкладки, дерево, отдельные панели?
