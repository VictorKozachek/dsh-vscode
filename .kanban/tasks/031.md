## Задача

Расширение запускает `dsh` без учёта того, что VS Code из GUI на macOS имеет
урезанный PATH. `dsh` — Node-скрипт с shebang `#!/usr/bin/env node`, поэтому
spawn падает с `env: node: No such file or directory` и кодом 127:
ACP не поднимается, панель показывает «менеджер сессий не подключён».

Диагностика из `Output → DSH` (VSIX dev7, 18.11):

```
ACP: запуск /opt/homebrew/bin/dsh (setting)
ACP stderr: env: node: No such file or directory
ACP: процесс завершился (127), перезапуск через 500 мс (попытка 1/5)
```

**Требования:**
1. При spawn передавать окружение, в котором `PATH` содержит каталог Node,
   которым работает расширение: `path.dirname(process.execPath)` в начало PATH
   (и не терять остальной PATH пользователя). Это чинит случай, когда
   `dsh.executablePath` указывает на скрипт с `env node`, а node нет в GUI PATH.
2. Если `dsh` — скрипт с shebang `#!/usr/bin/env node`, а node всё равно не
   находится — попробовать запуск через `process.execPath` (node dsh ...) как
   fallback, с записью в диагностику.
3. Диагностика: показывать, какой node/PATH использованы при spawn, и подсказку
   «укажите путь к node/dsh» вместо голого кода 127.
4. Тест: spawn с пустым PATH (`env -i`) + `dsh`-скрипт с `env node` — процесс
   стартует (мок-бинарь), без 127; тест на fallback через process.execPath.

## Исправления (`$(git rev-parse --short HEAD)`)

1. **PATH при spawn.** `buildSpawnEnvironment` клонирует окружение и ставит
   `path.dirname(process.execPath)` в начало `PATH`, сохраняя остальной PATH
   пользователя. Именно это окружение передаётся `spawn` для ACP — GUI-запуск
   VS Code без Homebrew теперь находит `node` для `#!/usr/bin/env node`.
2. **Fallback.** `isEnvNodeScript` читает shebang; если dsh — скрипт с
   `#!/usr/bin/env node`, а в исходном PATH нет каталога node, запускаем
   `process.execPath <dsh> ...` как fallback (с записью в диагностику). Иначе
   обычный запуск скрипта с исправленным PATH.
3. **Диагностика.** В `Output → DSH` пишется `ACP: node <execPath>; PATH <...>`
   и пометка `(fallback env node → process.execPath)`; при коде выхода 127 —
   подсказка «dsh не смог найти node (env node). Проверьте PATH или укажите
   путь к node/dsh в dsh.executablePath».
4. **Тесты:** `buildSpawnEnvironment` (node-каталог первым, остальной PATH цел),
   `isEnvNodeScript` (env-node/не-node), и интеграционный: `env -i PATH=/usr/bin:/bin`
   + мок `dsh` с `#!/usr/bin/env node` → ACP стартует через fallback
   `process.execPath`, `initialize` и `session/list` проходят, в логе видны
   node/PATH/fallback.

## Electron extension host (`$(git rev-parse --short HEAD)`)

1. **PATH больше не засоряется Electron-каталогом.** `buildSpawnEnvironment`
   определяет Electron (`process.versions['electron']` / тестовый
   `electronRuntime`) и в этом режиме не добавляет `dirname(process.execPath)` —
   там нет node; PATH пользователя сохраняется.
2. **Fallback через сам Electron.** `buildSpawnPlan` для env-node shebang без
   node в PATH (и для `.mjs`-скриптов) запускает
   `process.execPath <dsh> ...` с `ELECTRON_RUN_AS_NODE=1`; обычный node-режим
   по-прежнему использует `process.execPath` как node. Это работает и в
   extension host VS Code, где `process.execPath` — Electron/Code Helper.
3. **Диагностика** пишет `ACP: node <execPath> (Electron,
   ELECTRON_RUN_AS_NODE=1); PATH ...` и fallback; подсказка при 127 осталась.
4. **Тесты:**
   - unit `buildSpawnPlan` для Electron: executable = process.execPath, args =
     `[dsh, ...]`, `ELECTRON_RUN_AS_NODE=1`, fallback, PATH без Electron-каталога;
   - representative-интеграция с **реальным Electron** (DeepSeek Harness app,
     `ELECTRON_RUN_AS_NODE=1`) и мок `dsh` с `#!/usr/bin/env node`,
     `PATH=/usr/bin:/bin` без node → `initialize` и `session/list` проходят;
     при отсутствии Electron-бинаря тест скипается;
   - прежний node-тест `env -i` сохранён как unit.
