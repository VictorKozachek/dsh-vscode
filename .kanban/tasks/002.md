## Задача

Реализовать `WorkspaceResolver` — компонент, который по открытой папке говорит,
какой это воркспейс и как его опознать между запусками.

- `extension/src/workspace/resolver.ts`: `resolveWorkspace(folders)` →
  `{ id, path, name, remote, gitRemote, multiRoot, primary }`.
- Канонический путь: `fs.realpath`, нормализация регистра на `darwin`/`win32`,
  учёт смены раскладки.
- `gitRemote`: чтение `.git/config` без внешних зависимостей; нормализация
  `git@github.com:org/repo.git` → `github.com/org/repo`; поддержка `git worktree`.
- `remote`: `vscode.env.remoteName` (`ssh`/`wsl`/`containers`) как часть ключа.
- `id`: `sha256(remote | path | gitRemote)[:16]` — путь входит в ключ **всегда**:
  две папки одного репозитория (`repo/frontend` и `repo/backend`) — разные
  воркспейсы; переезд папки даёт новый воркспейс (перенос истории — v0.2).
- Multi-root: primary — первая папка; `.code-workspace` определяется.
- Unit-тесты на временных каталогах: без открытой папки, одиночный корень,
  вложенные папки, симлинк, смена регистра, git-репозиторий без remote.

## Критерии готовности

- [ ] `resolveWorkspace` возвращает стабильный `id` для одного и того же пути
      при повторных вызовах и после рестарта; разные пути одного репозитория дают
      разные `id`.
- [ ] Ни одного `child_process` вызова на горячем пути: только чтение файлов.
- [ ] Тесты покрывают все перечисленные случаи; `node --test` зелёный.
- [ ] Публичный API задокументирован в `extension/src/workspace/README.md`.

## Решение оркестратора (2026-11-09)

Ревью #002 вскрыло противоречие: требование «id переживает переезд папки» несовместимо
с путём в ключе. Решение:

- `id = sha256(remote | canonical path | gitRemote)[:16]` — **путь входит в ключ
  всегда**. Две папки одного репозитория — разные воркспейсы; переезд папки даёт
  новую запись реестра, перенос истории между записями — отдельная задача v0.2.
- §4.1 `SPECIFICATION.md` обновлён синхронно (этот репозиторий, коммит оркестратора).
- Что сделать исполнителю: реализовать формулу с путём; тест «id переживает
  переезд» заменить на «разные пути одного репозитория дают разные id»; README —
  под это поведение.
- `engines.node` поднят оркестратором до `>=22.18` (тесты импортируют `.ts`
  напрямую), отдельно править не нужно.

### Замечания ревьювера — что сделано

1. **`id` не совпадал с карточкой** (путь не входил в ключ при наличии
   `gitRemote`). Реализована формула `sha256(remote | путь | gitRemote)[:16]`;
   тест «id переживает переезд» заменён на «разные папки одного репозитория
   дают разные `id`» + отдельный unit-тест `workspaceId` (воспроизводит кейс
   `repo/frontend` vs `repo/backend`); README переписан под новое поведение,
   `resolveWorkspace` JSDoc тоже.
2. **Недостижимая проверка `normalizedHost === 'file'`** в `normalizeGitRemote`
   удалена: протокол `file` отфильтрован выше, `file:///…` по-прежнему даёт
   `null` (есть в таблице тестов).
3. **Импорт `.ts` в тестах и `engines.node`** — снято оркестратором: engines
   подняты до `>=22.18` (type stripping), правок не потребовалось.
